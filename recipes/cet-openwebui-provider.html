CET OpenAI-kompatiblen Provider mit Prüfsatz abnehmen

Vor der Anbindung an Open WebUI hilft ein kleiner, reproduzierbarer Prüfsatz: Erst wird die Form synthetischer Modell- und Chat-Antworten lokal kontrolliert. Erst danach folgt – in einem ausdrücklich erlaubten Testkontext – der echte Endpoint-Test.

Suchintention

OpenAI kompatiblen Provider testen: Entwickler:innen möchten Modellliste, Antwort-Envelope und sichtbare Abschlussmetadaten prüfen, ohne sofort Tokens oder echte Fachdaten einzusetzen.

Prüfgrenze

Das Beispiel bewertet nur die technische Form einer eingebetteten Fixture. Es sagt nichts über Fachrichtigkeit, Datenschutz, SLA, Preise oder Produktivreife aus.

CTA

Wenn aus dem lokalen Formtest ein kontrollierter Integrationsreview werden soll: Felix Mertens kann Testgrenze und fachlichen Prüfsatz einordnen.

Lokaler Dry-Run

node examples/cet-openai-provider-acceptance.js

Das Skript prüft ohne Netzwerkzugriff:

  • eine Modellliste mit mindestens einer Modell-ID,
  • eine Chat-Completion mit Assistant-Rolle und nichtleerem Inhalt,
  • die Referenz des Antwortmodells auf die Modellliste,
  • sichtbaren Abschlussgrund und dokumentierte Nutzungsmetadaten.

Erwartetes Ergebnis

{
  "mode": "cet-openai-provider-acceptance",
  "sourceClass": "synthetic-local-fixture",
  "networkCalls": 0,
  "tokenRequired": false,
  "passed": true
}

Danach: erlaubter Endpoint-Test

  1. Separaten Test-Tenant und Test-Token verwenden.
  2. Modellliste abrufen und Modell-ID protokollieren.
  3. Eine synthetische, fachlich harmlose Frage senden.
  4. Status, Antwortform, Modell-ID und Abschlussgrund dokumentieren.
  5. Technische Kompatibilität getrennt von fachlicher Qualität bewerten.

Keine echten Kundendaten, Marktkommunikationsdateien oder internen Prompts hochladen. Ein erfolgreicher Formtest ist keine Freigabe für den Produktiveinsatz.
